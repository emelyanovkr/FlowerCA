# План API заявок и сертификатов

Дата: 2026-10-08. Документ описывает план и статус его инкрементальной реализации.
Основание: пользователь согласовал процесс «заявка → решение администратора → сертификат»
и инкрементальную реализацию с тестами и ревью. Активная работа отслеживается в
`.agent-notes/current-work.md`; отметки ниже ставятся только после реализации и проверки.

## Границы первой версии

- Пользователи запрашивают личные сертификаты `USER_CLIENT` для входа в экосистему Flower.
- Заявочная модель не выпускает `ADMIN_CLIENT` или доменные `TLS_SERVER`.
- Администратор работает через существующую mTLS-аутентификацию и authority `ADMIN`.
- Клиент генерирует ключ локально и передаёт только PEM CSR, не приватный ключ.
- Email, имя и организация из заявки являются заявленными данными. Подпись CSR доказывает
  владение ключом, но не подтверждает личность, email, организацию или административную роль.
- Subject/SAN выпускаемого сертификата формируются из одобренного профиля, не из CSR.
- Подтверждение email и способ первого входа отложены по решению пользователя. Это блокирует
  полный first-time onboarding, но не чтение данных администратором и разработку внутренней
  модели заявок. Не добавляем вместо решения анонимную выдачу или открытый доступ к заявкам.
- Frontend, импорт сторонних сертификатов, OCSP/CRL, operator recovery и расширенное управление
  пользователями не входят в первые инкременты. ИБ-ревью модельным агентом остаётся в конце.

## Что уже реализовано

| Метод и путь | Функция |
| --- | --- |
| `GET /api/v1/public/probe` | Безопасная публичная проверка транспорта |
| `POST /api/v1/admin/users` | Создать обычный USER / ACTIVE и success audit |
| `POST /api/v1/admin/certificates/renew` | Продлить сертификат текущего администратора до expiry |

Bootstrap первого администратора — операторская процедура, не публичный endpoint.
Эти операции сохраняются. Создание пользователя не выпускает сертификат.

## Целевые маршруты администратора

Все маршруты требуют пригодный зарегистрированный `ADMIN_CLIENT` и активного ADMIN-владельца.
Новые application services дополнительно защищаются method security. Не возвращаем JPA entities.

| Метод и путь | Функция | Инкремент |
| --- | --- | --- |
| `GET /api/v1/admin/certificates` | Пагинированный список сертификатов | 1 |
| `GET /api/v1/admin/certificates/{id}` | Карточка сертификата | 1 |
| `GET /api/v1/admin/certificate-requests` | Пагинированный список заявок | 2 |
| `GET /api/v1/admin/certificate-requests/{id}` | Детали заявки | 2 |
| `POST /api/v1/admin/certificate-requests/{id}/reject` | Отклонить ожидающую заявку с причиной | 3 |
| `POST /api/v1/admin/certificate-requests/{id}/issue` | Одобрить данные и выпустить USER_CLIENT по заявке | 4 |
| `GET /api/v1/admin/certificates/{id}/chain` | Получить PEM цепочку конкретного сертификата | 4 |
| `POST /api/v1/admin/certificates/{id}/revoke` | Отозвать USER_CLIENT с причиной | 5 |

Отдельный прямой `POST /api/v1/admin/certificates` не реализуем в этой версии: выпуск идёт
по заявке. `/issue` объединяет административное одобрение и выпуск; промежуточный
`APPROVED` и отдельный `/approve` пока не нужны. Результат отзыва не удаляет сертификат.
Политика отзыва админских сертификатов требует отдельного решения, чтобы не создать
непредусмотренный lockout единственного администратора.

## Целевые маршруты пользователя

Для инкремента 6 это клиент с уже имеющимся пригодным сертификатом и активным владельцем.
Доступ только к своим объектам, owner определяется сервером из principal, не из email или
переданного `userId`. First-time доступ к тем же операциям требует решения из инкремента 7.

| Метод и путь | Функция | Инкремент |
| --- | --- | --- |
| `POST /api/v1/certificate-requests` | Подать новую заявку с CSR | 6 / 7 |
| `GET /api/v1/certificate-requests` | Получить только свои заявки | 6 / 7 |
| `GET /api/v1/certificate-requests/{id}` | Посмотреть только свою заявку | 6 / 7 |
| `POST /api/v1/certificate-requests/{id}/cancel` | Отменить свою ожидающую заявку | 6 / 7 |
| `GET /api/v1/certificates` | Получить только свои сертификаты | 6 / 7 |
| `GET /api/v1/certificates/{id}` | Посмотреть только свой сертификат | 6 / 7 |
| `GET /api/v1/certificates/{id}/chain` | Скачать цепочку своего сертификата | 6 / 7 |

Пользовательский `/revoke` пока не включён: пользователь явно согласовал отзыв администратором.
Кнопка самостоятельного отзыва на макете остаётся отдельным вопросом, не автоматической
авторизацией расширить API. Просмотр CSR/персональных данных не становится публичным.

## Жизненный цикл

Базовые состояния заявки: `PENDING_REVIEW`, `ISSUED`, `REJECTED`, `CANCELLED`.
Переходы из `PENDING_REVIEW` в terminal states контролируются сервисом под блокировкой.
До определения onboarding никакой новый пользователь не считается проверенным по email.
Если подтверждение email станет обязательным, добавим отдельный этап допуска заявки;
отложенное подтверждение нельзя представлять как выполненное.

Сертификат имеет собственную жизнь: действует, истёк либо отозван. Истечение определяется
с учётом `notBefore`/`notAfter`, а не только потенциально устаревшего поля status.
Отзыв не превращает выданную заявку в отклонённую. Историю сохраняем.

Одна заявка с неизменным CSR соответствует не более чем одному выпущенному сертификату.
Повтор успешного `/issue` возвращает ранее сохранённый результат, не подписывает заново.
Новые ключи или повторная заявка после отказа — новая заявка, а не изменение обработанной.

## Инкременты и критерии ревью

### 1. Административный список и карточка сертификата — следующий шаг

Реализация добавлена через Hibernate/JPA Criteria scalar projections; пользователь выбрал
сохранить JPA и отложить performance measurements. Контракт и пример запросов — в
`admin-mtls-api.md`, раздел Read the certificate registry. Unit-тесты новых DTO/пагинации/статусов:
18 passed, 0 failures/errors/skipped; расширенный unit-прогон без Docker — 75 passed,
0 failures/errors/skipped. MySQL/HTTP integration tests добавлены, но первый запуск
дал 1 initialization failure из-за недоступного Docker, сценарии не выполнялись.
Поэтому инкремент ещё не закрыт и галочки ниже остаются пустыми до полной проверки.

Обновление 2026-10-09: пользователь согласовал объединение read/renewal в
`AdminCertificateController` / `AdminCertificateService`, JPQL DTO-запросы в общем
`CertificateRepository` и `Pageable` на входе. Отдельный режим чтения с отключённой выдачей
больше не требуется; критерий ниже отменён, а не выполнен. Предыдущие цифры относятся к
старой реализации, проверка рефакторинга отслеживается в current-work.md.

Результат рефакторинга: 88 unit tests passed, 0 failures/errors/skipped, включая проверку
синтаксиса/типов JPQL без выполнения SQL. MySQL read + renewal: 0 passed, 9 failures,
0 errors/skipped — недоступный Docker не позволил загрузить контексты, сценарии не выполнялись.
Инкремент остаётся открытым до интеграционного прогона; полный suite пока не повторялся.

- [ ] Два GET endpoint из таблицы; read-only методы общего AdminCertificateService с method security.
- [ ] Явные DTO и стабильный формат страницы, ограниченный page size, разрешённые sort fields.
- [ ] Минимальные фильтры: owner UUID, certificate profile, эффективный статус.
- [ ] Отображаем сроки, owner UUID/имя/email, issuer, serial/fingerprint, профиль и сведения
  об отзыве. Не кладём DER/PEM и произвольные entity graphs в каждую строку списка.
- [ ] Неправильные параметры → безопасный 400, отсутствующий сертификат → безопасный 404.
- [ ] Отменено пользователем 2026-10-09: GET работает при выключенном online issuer.
  Все certificate admin endpoints теперь доступны только с включённым модулем выдачи;
  отдельный режим чтения не реализуем. Оставлено unchecked как отменённое требование.

### 2. Модель заявок и чтение администратором

- [ ] Модель `CertificateRequest`, статусы, immutable CSR/заявленные данные, даты,
  привязка к доказанному владельцу, решение и ссылка на выданный сертификат.
- [ ] Развести claimed data и approved identity; нельзя автоматически присоединять заявку
  к существующему аккаунту или менять его данные по одному совпадению email.
- [ ] Новая Flyway-миграция, не переписывание V1/V2. Уточнить актуальное применение перед
  schema work; ранее миграции применялись к тестовым схемам, persistent статус сейчас неизвестен.
- [ ] Admin list/detail с ограниченной пагинацией и фильтрами по статусу/дате/имени/email.
- [ ] Не добавлять анонимный или production test-only endpoint для заполнения списка.
  До подачи реальных заявок допускается пустой список; integration fixtures создаются в тестах.
- [ ] Тесты хранения, owner/result связей, 401/403/404, страниц/фильтров, статусов и границ DTO.
- [ ] Ревью инвариантов и migration diff. Это ещё не полный пользовательский сценарий.

### 3. Отклонение заявки

- [ ] `/reject`, bounded reason, ADMIN method security и revalidation действующего actor.
- [ ] Блокировка строки, разрешённые переходы, одинаковый повтор не дублирует success audit.
- [ ] Решение + actor-attributed audit в одной транзакции; failure/denial audit отдельно.
- [ ] Тесты повторов, гонок с другим решением, terminal-state conflict, rollback аудита и доступа.
- [ ] Ревью транзакции, блокировок и отсутствия частичного изменения заявки.

### 4. Выпуск по заявке и скачивание цепочки

- [ ] `/issue` выпускает исключительно USER_CLIENT из неизменного проверенного CSR;
  owner и одобренная identity устанавливаются доверенным процессом, не из CSR claims.
- [ ] Явный approved-owner binding; создание профиля для нового человека не включать
  автоматически до определения допуска первой заявки и правила привязки владельца.
- [ ] Request transition, certificate persistence, issuance/decision audit — один commit.
- [ ] Не более одного сертификата на заявку, включая параллельные действия и повтор после
  потерянного HTTP-ответа; проверить DB constraint и корректный порядок блокировок.
- [ ] Не возвращать PEM до commit. Неверный CSR/ключ/размер и конфликт состояния безопасно
  отклоняются; expired issuer, DB failure и audit rollback не создают committed result.
- [ ] `/chain` строится из конкретного leaf и его persisted issuer; не подмешивать цепочку
  текущего online issuer при просмотре старого сертификата после ротации. Root опционален.
- [ ] Тесты CSR spoofing, профиля и владельца, EKU/SAN, validity, concurrent issue/reject,
  idempotency, rollback, chain correctness и HTTP/method access.
- [ ] Ревью сохранения авторизации, identity, transaction boundaries и PKI инвариантов.

### 5. Административный отзыв USER_CLIENT

- [ ] `/revoke`: bounded reason, timestamp и REVOKED, ADMIN actor; row locks и success audit.
- [ ] Идемпотентность, consistency status/revokedAt/reason, согласованный порядок блокировок.
- [ ] Данные не удаляются; повтор не меняет первоначальные сведения и не дублирует успех.
- [ ] Тесты повторов/конкуренции, audit rollback, unknown ID, неразрешённого профиля и запрета
  использования отозванного сертификата в последующих проверках приложения.
- [ ] Ревью: это отзыв в реестре FlowerCA, не доказательство отказа всех внешних TLS-клиентов.
  OCSP/CRL или согласованная проверка реестра внешними сервисами — отдельный этап.

### 6. Кабинет существующего пользователя и повторные заявки

- [ ] User authorization требует пригодный USER_CLIENT, активного владельца и проверки

- [ ] User request creation/list/detail/cancel и certificate list/detail/chain из таблицы.
- [ ] Первая запись request создаётся с доверенной identity текущего клиента; CSR только
  для нового сертификата, не способ самостоятельно выбрать другого владельца или ADMIN_CLIENT.
- [ ] Проверить временное окно подмены owner/status при мутациях и восстановление доступа
  после expiry: этот этап не обещает recovery, не имеет анонимного обхода.
- [ ] Тесты чужих UUID/owner filter, BLOCKED/absent owner, TLS_SERVER, revoked/expired,
  переходов cancel/issue/reject и отсутствия выдачи чужих данных.
- [ ] Реальный TLS 1.3 smoke для user flow; MockMvc отдельно проверяет прикладные ветки.
- [ ] Ревью всего доступа к своим объектам, метода и URL, без доверия CN/email/CSR claims.

### 7. Первая заявка без сертификата — ждёт решения о первом входе

- [ ] Согласовать аутентификацию/допуск, доступ к собственной заявке до выдачи, привязку

- [ ] Email verification не реализовывать до решения пользователя. Не заменять её

- [ ] Уточнить API подтверждения/входа и отдельный ограниченный admission path, если потребуется.
- [ ] После решения реализовать лимиты, replay/idempotency, credential expiry и audit.
- [ ] Тесты end-to-end нового пользователя, обхода admission, чужих заявок, повторов и abuse.
- [ ] Ревью first-time сценария; финальное ИБ-ревью агентом в согласованной завершающей стадии.

## Правило перехода к следующему инкременту

Для каждого изменения: краткий контракт → небольшой implementation diff → unit/integration
tests → self-review финального diff → исправления → отчёт → решение о следующем инкременте.
Независимое агентское ревью не подразумевается на каждом шаге; отдельно запланировано в конце.
Показываем passed/failed/errors/skipped; Docker обязателен для MySQL integration tests.
После изменения криптографии/аутентификации дополняем TLS 1.3 проверки по риску.
Когда практично, запускаем полный `./gradlew test`; исторические 90 passed не выдаём за новый run.
Не создаём коммиты без явного запроса пользователя, не трогаем unrelated changes.

Обязательные review themes: доступ и ownership, CSR input limits, approved identity, transitions,
конкуренция и транзакции, аудит, отсутствие секретов, HTTP errors, schema compatibility.
Findings помечаем как actual defect, missing coverage или future hardening; исправления и
остатки сохраняем в `.agent-notes/issues.md`.
